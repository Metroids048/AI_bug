# 个人挖洞最核心的思路

真正有经验的研究员，不是拿几十个工具一顿扫。

更接近下面这个过程：

```text
选一个值得长期看的目标
↓
先理解产品和功能
↓
知道哪些用户/角色能做什么
↓
从请求和业务流程里找“不符合预期”的地方
↓
把异常进一步变成安全影响
↓
稳定复现
↓
再提交
```

---

# 1. 先选对目标，比会多少漏洞更重要

同样一个小时：

- 在竞争极高、所有人都盯着的核心主站；
- 和在刚上线、刚收购、边缘业务、旧系统、冷门子域；

得到结果的概率完全不同。

因此选 Target 时应看：

- Program Scope 是否够大；
- 是否有大量业务系统；
- 是否经常新增资产；
- 是否存在子公司/收购公司；
- 是否有复杂登录和角色；
- 是否有 API；
- 是否有新功能；
- 是否有移动端和 Web 多套入口；
- 是否有冷门资产。

这和传统“漏洞扫描”的差别非常大：

**先找值得挖的地方，再谈挖什么。**

---

# 2. 不要一打开网站就开始“打 Payload”

更有效的第一步是理解：

```text
这个产品是干什么的？
有哪些用户？
用户之间是什么关系？
谁能创建谁？
谁能查看谁？
谁能删除谁？
谁能审批谁？
哪些功能需要付费？
哪些功能需要特定角色？
```

因为很多高价值漏洞本质上不是复杂技术问题，而是：

> 系统允许某个用户做了本来不应该做的事情。

---

# 3. 两个测试账号非常重要

如果你只有一个账号，很难验证权限类漏洞。

最好准备：

```text
Account A：攻击者视角
Account B：受害者视角，但也是你自己控制的测试账号
```

然后不断做差异测试：

```text
A 创建的数据，B 能看到吗？
B 的对象 ID 给 A，A 能读吗？
A 能修改 B 的对象吗？
低权限角色能调用高权限接口吗？
退出登录后还能调用吗？
```

只用自己控制的账号，避免影响真实用户。

---

# 4. 重点看“请求”，不要只看网页按钮

网页上没有按钮，不代表后端接口不存在。

研究过程中应该关注：

- 浏览器 Network；
- API 请求；
- JSON 参数；
- Cookie；
- Token；
- 对象 ID；
- 用户 ID；
- role / permission；
- GraphQL；
- JS 里隐藏的 endpoint。

很多问题都是：

```text
UI 不给你这个功能
但是接口其实还接受
```

或者：

```text
UI 隐藏了某个按钮
但是只要手动调用 API 就能执行
```

---

# 5. 发现异常后，不要马上报

这是新手特别容易犯的错。

先把异常分成三层：

## 第一层：Observation

只是发现“不太对”。

例如：
- 两种用户返回不同错误；
- 一个不应该出现的接口存在；
- 某个字段能被修改；
- 某个对象 ID 可以替换。

## 第二层：Exploit

证明攻击者能利用。

例如：
- A 能读取 B 的订单；
- 普通用户能修改管理员设置；
- 免费用户能调用付费接口。

## 第三层：Impact

证明真实后果。

例如：
- 敏感信息泄露；
- 越权修改；
- 删除他人数据；
- 账户接管；
- 绕过付费；
- 绕过审批；
- 获得更高权限。

只有走到后面两层，才越来越像真正有价值的 Bug Bounty。

---

# 6. 越权和业务逻辑特别适合人工思考 + AI执行

很多扫描器擅长找：

- 已知版本漏洞；
- 明显配置；
- 常见注入点。

但是：

```text
这个优惠券为什么只能用一次？
这个角色为什么不能审批？
这个订单状态为什么不能回退？
这个用户为什么不能看到那个项目？
```

这些需要先理解业务。

AI 很适合帮你：

- 阅读流程；
- 比较账号；
- 生成请求；
- 批量修改参数；
- 做状态对比；
- 记录结果。

但“为什么这里不合理”仍然需要一个清晰的业务假设。

---

# 7. 不要只追求高危，先追求“真实 + 可复现”

新手最容易被“Critical”“RCE”“0day”吸引。

但第一阶段更重要的是：

- 报告真的成立；
- 证据清楚；
- 审核人员能复现；
- 没违反 Scope；
- 不影响真实用户。

一个稳定的中危问题，比一个模型脑补出来的 Critical 更有价值。

---

# 8. 重复（Duplicate）是 Bug Bounty 的常态

你找到的漏洞可能是对的，但别人已经先报了。

所以长期赚钱不能只靠：

```text
大家都知道的热门资产
+
大家都扫的热门漏洞
```

应该逐渐提高自己的差异化：

- 冷门资产；
- 新资产；
- 新功能；
- 收购公司；
- 隐藏 API；
- 复杂角色；
- 业务逻辑；
- 漏洞链；
- 自己的自动化和长期监控。

---

# 9. 每一次失败都应该留下记录

真正有用的经验库不应该只有成功报告。

还应该记：

```text
这个 Target 为什么没找到？
什么假设验证失败？
什么地方已经有完整权限检查？
什么路径浪费了很多时间？
什么 Finding 最后被判 Informative？
什么报告 Duplicate？
```

以后 AI 的 RAG 如果只有成功样本，会产生严重偏差。

正确的知识库应该同时有：

- Positive Case；
- Safe Control；
- Failed Hypothesis；
- Duplicate；
- N/A；
- Informative；
- Accepted Finding。

---

# 10. 长期挖一个项目，比天天换项目更容易形成优势

当你长期看同一个 Program，会逐渐知道：

- 它的技术栈；
- 常见接口；
- 业务习惯；
- 它过去出过什么问题；
- 它的开发团队常犯什么错误；
- 哪些资产经常更新；
- 哪些漏洞类型它奖励高。

这种积累会形成 Program-specific Memory。

对 AI 来说更明显：

```text
通用安全知识
+
这个 Program 的历史
+
你自己的历史报告
=
更有效的研究上下文
```

---

# 最后只记 6 句话

1. **先理解产品，再测试。**
2. **先找权限和业务边界，再找“漏洞名”。**
3. **异常不等于漏洞，必须证明可利用和影响。**
4. **两个自控测试账号是权限测试的基础设施。**
5. **不要让成功样本把 RAG 带偏，失败样本也要保留。**
6. **长期积累一个 Program 的 Memory，比不停换目标更有复利。**

---

# 最少术语

- IDOR：改一个对象 ID 后，能访问别人的对象。
- BAC / Broken Access Control：权限控制失效的总称。
- Business Logic：业务流程本身的规则。
- Duplicate：别人已经先报过。
- Informative：有信息价值，但不被认定为有效安全漏洞。
- N/A：平台认为不属于有效漏洞。
