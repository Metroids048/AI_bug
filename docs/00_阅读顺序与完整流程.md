# 整条链路只记这一张图

```text
选择平台
↓
选择 Program（项目）
↓
阅读 Scope（哪些目标允许测试）
↓
选 Target（具体网站/API/应用）
↓
Recon（先把资产和功能看清楚）
↓
提出漏洞假设
↓
用请求/账号/参数做验证
↓
确认是否真的能越权、泄露、绕过、修改
↓
至少稳定复现
↓
证明 Impact（到底会造成什么后果）
↓
整理 Evidence（请求、响应、截图、日志）
↓
写 Report
↓
平台/厂商 Triage（审核）
↓
Valid / Duplicate / N/A / Informative
↓
Bounty
```

对 AI_bug 项目来说，真正需要自动化的是中间这一段：

```text
理解 Scope
→ Recon
→ 建立假设
→ 设计验证
→ 执行
→ 收集证据
→ 反驳自己
→ 判断 Impact
→ 复现
→ 生成报告草稿
```

但最终提交前仍应保留人工确认。

# 你现在只需要理解的 12 个词

| 词 | 白话解释 |
|---|---|
| Bug Bounty | 厂商授权你找安全问题，找到有效问题后可能给奖金 |
| Program | 某个厂商在平台上开的漏洞项目 |
| Scope | 明确允许你测试哪些域名、APP、API，以及禁止什么 |
| Target | 你实际准备研究的某个网站/API/功能 |
| Recon | 先把目标摸清楚：有哪些页面、接口、子域、角色和功能 |
| Finding | 发现了一个异常现象，但还不一定是漏洞 |
| Vulnerability | 已经能证明是安全问题 |
| Impact | 这个问题到底能造成什么真实后果 |
| PoC | 最小可复现证明 |
| Report | 提交给厂商的漏洞报告 |
| Triage | 厂商/平台审核漏洞是否成立、严重度如何 |
| Duplicate | 别人已经先报过同一个问题，所以通常拿不到奖金 |

# 最重要的三个判断

## 1. “发现异常”不等于“找到能赚钱的漏洞”

比如：
- 某接口报错不同；
- 某响应里多了一个字段；
- 某配置看起来不安全；

都只是线索。

要继续问：
- 攻击者能利用吗？
- 能读到不该读的数据吗？
- 能做不该做的操作吗？
- 能绕过认证、权限、支付、次数、角色限制吗？
- 能稳定复现吗？
- 项目规则里接受这种问题吗？

## 2. AI 的核心价值不只是“扫描”

更有价值的是：
- 帮你读大量页面和 JS；
- 归纳 API；
- 自动生成和修改请求；
- 自动比较两个账号的权限差异；
- 自动尝试复杂但重复的验证；
- 从过去的漏洞报告里学习模式；
- 帮你写脚本；
- 长时间执行；
- 自动整理 Evidence 和 Report。

## 3. 真正值钱的是“Impact + 可复现 + 低重复率”

一个报告能不能拿钱，往往取决于：
- 是否真实；
- 是否影响够大；
- 是否还没人报；
- 是否能让审核人员快速复现；
- 是否符合 Scope；
- 是否不是理论问题。

不要把“收益数字”当作模型判断漏洞价值的主要依据。
优先检索：
- 具体漏洞模式；
- 成功/失败原因；
- 验证步骤；
- 风险边界；
- 报告结构；
- 人工复核点。
